# agent-sandbox v0.1: how often do AI agents make payment mistakes?

*Draft. Everything below describes what is built and how it measures. The findings section is
empty on purpose: no real model has been run yet, and no number will appear here before it has.*

## What we built

agent-sandbox is an open-source sandbox for measuring how well AI agents do real work, one domain
("world") at a time, on a shared, domain-neutral kit. v0.1 releases the first world, **payments**,
and its task set `payments-v0.1`.

The payments world simulates UPI-inspired rails built from public concepts only (accounts with
test-format handles, recurring, one-time and reserve-style mandates, per-payment, daily and
per-merchant caps, idempotency keys, refunds and a double-entry ledger), merchants with reliability
profiles (catalogues, offers, carts, orders, subscriptions, invoices and pages, where promised and
actual delivery differ), and after-payment operations (refund requests, disputes with windows and
deemed acceptance, reconciliation, a support inbox). The failures are the point: insufficient
funds, caps that change, expired or revoked mandates, timeouts where the payment actually went
through, status that lags, offers that are not what they say, merchants that look like the real
one.

Nothing is real: no real rail, money, handle or customer data, and no network inside the world.

## Method

**Tasks.** 50 public tasks: 15 on the rails, 15 in commerce, 12 in disputes and 8 that span them;
15 easy, 20 medium and 15 hard. Each is a user's request in plain words ("Set up autopay for my
gym... Don't let them take more than that in one go"), the world's initial state, the tools the
agent may use, and a step cap. Ten tasks are passed only by *not* paying, and asking the user
instead.

**The agent.** One reference tool-calling agent with a fixed, versioned system prompt
(`payments/v1`), at temperature 0, calling the world's 25 tools over MCP. A run ends when the model
replies without a tool call, calls a terminal tool (`ask_user`), or hits a cap (steps, tokens or
cost). Models are called through LiteLLM, so any provider or a local model can be measured the
same way.

**Grading.** Deterministic Python over the world's final state and the trace of tool calls,
never the agent's words, and no LLM judge. A run passes only if every check passes. A failed run is
labelled with the mistake that matters most: overspending, paying the wrong merchant, paying twice,
ignoring a limit, paying when it should have asked (the high-impact ones), falling for a fake
discount, not recovering a refund, or raising an unwarranted claim. Every task ships a golden run
that must pass and at least one plausible wrong run that must fail with its declared type; CI plays
all of them.

**Scores.** Each task runs three times. `overall` is the mean over tasks of each task's pass rate,
with a 95% bootstrap interval over tasks. `task_success_rate` is the share of tasks passed in every
run, and `safe_action_rate` the share of runs with no high-impact money mistake.

**Stress.** Seven seeded modifiers make tasks harder without changing the job: misleading page
content, conflicting instructions, time pressure, a flaky payment service, a cap that drops
mid-task, a fake offer and a look-alike payee. The stressed set `payments-v0.1-stressed` has 33
tasks, each with its own golden and trap runs. A calibration report measures how much each modifier
lowers each model's score.

**Hidden set.** 17 tasks kept in a private repository, published only as hashes, scored only as an
aggregate next to the public score.

**Reproducibility.** The same actions always give the same score: seeded randomness, a simulated
clock, exact snapshots of every service. `sandbox verify` replays each run's recorded actions on a
fresh world and checks every response and every grade. The run directories behind the leaderboard
will be attached to the GitHub release, and `sandbox submission check` verifies any of them.

## Setup

```bash
pip install 'agent-sandbox-bench[litellm]'
sandbox quickstart --model <litellm-id>         # ten tasks, one run each, a score
sandbox run --world payments --tasks payments-v0.1 --model <litellm-id> --runs 3 --out runs/<m>
sandbox verify --run runs/<m>
```

## Limitations

- A simulation from public documentation. Several windows are invented or rest on secondary
  reports, and are recorded as parameters for the payments reviewer. A good score here says an
  agent does well in this simulation, not that it is safe to give it a real account.
- No domain reviewer has signed off the graders yet, so the world is `preview`.
- 50 public tasks: the intervals are wide, and small differences between models mean nothing.
- One harness: scores are of a model inside this runner's loop and prompt.
- Graders read state, not words: whether an agent explains itself or asks a good question is not
  graded, only that it asked after seeing the problem.
- The v0.1 hidden set is weak by construction: seeded variants of public tasks under public
  modifiers. It catches copied answers and leaks, not transfer to new kinds of work.
- A replay proves a run is consistent, not that a model produced it; submissions are also
  spot-checked by rerunning a sample with the model.
- Not tested at all: fraud detection, credit or KYC, other currencies, NPCI's own codes, the
  interbank dispute process, returns and pre-debit notices.
